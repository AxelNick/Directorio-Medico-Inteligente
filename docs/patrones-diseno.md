# Patrones y decisiones de diseño implementados

Revisión del código: 23 de octubre de 2026. Esta guía sirve para ubicar ejemplos concretos durante la exposición. **Patrón GoF** y **patrón de arquitectura o aplicación** se distinguen abajo; usar una biblioteca que implementa un patrón no equivale a haber escrito toda su infraestructura.

## Patrones GoF presentes mediante frameworks

| Patrón | Ubicación y evidencia | Cómo explicarlo en la exposición |
| --- | --- | --- |
| **Proxy** (estructural) | [AuditoriaAspect.java](../backend/src/main/java/pe/edu/uni/backend/aspect/AuditoriaAspect.java) declara `@Aspect`, `@Around` y `@AfterReturning` sobre métodos de `MedicoService` y `EspecialidadService`. [AuditoriaService.java](../backend/src/main/java/pe/edu/uni/backend/service/AuditoriaService.java) guarda los eventos. | Spring AOP crea el proxy del servicio. Al actualizar un perfil, el aspecto observa la llamada y registra los campos cambiados tras el retorno del método. **El equipo escribió el aspecto; Spring genera el proxy.** No afirmar que el evento ya está confirmado en base de datos solo por haber retornado `proceed()`. |
| **Chain of Responsibility** (comportamiento) | [SecurityConfig.java](../backend/src/main/java/pe/edu/uni/backend/security/SecurityConfig.java) inserta `JwtAuthFilter` en `SecurityFilterChain` mediante `addFilterBefore`. [JwtAuthFilter.java](../backend/src/main/java/pe/edu/uni/backend/security/JwtAuthFilter.java) valida el token, establece la autenticación y llama a `filterChain.doFilter(...)`. | La solicitud atraviesa una cadena de filtros de Spring Security. Nuestro filtro aporta la validación JWT y pasa la solicitud al siguiente eslabón. **La cadena la proporciona Spring; el filtro JWT sí es código del proyecto.** |

## Patrones de arquitectura y aplicación

| Patrón o técnica | Ubicación y evidencia | Cómo explicarlo en la exposición |
| --- | --- | --- |
| **Arquitectura por capas** | [MedicoController.java](../backend/src/main/java/pe/edu/uni/backend/controller/MedicoController.java) recibe HTTP y delega; [MedicoService.java](../backend/src/main/java/pe/edu/uni/backend/service/MedicoService.java) aplica reglas; [MedicoRepository.java](../backend/src/main/java/pe/edu/uni/backend/repository/MedicoRepository.java) accede a persistencia; [Medico.java](../backend/src/main/java/pe/edu/uni/backend/entity/Medico.java) modela la entidad. | Seguir `PUT /medicos/me/perfil`: controlador → servicio → repositorio/entidad → DTO de respuesta. La auditoría intercepta el servicio mediante AOP. Es una organización de responsabilidades, no un patrón GoF. |
| **Repository** | [MedicoRepository.java](../backend/src/main/java/pe/edu/uni/backend/repository/MedicoRepository.java) y [AuditoriaRepository.java](../backend/src/main/java/pe/edu/uni/backend/repository/AuditoriaRepository.java) extienden `JpaRepository`; los servicios llaman a sus métodos sin escribir SQL en esas clases. En frontend, [audit.ts](../frontend/src/data/audit.ts) define `AuditRepository` y [mockAuditRepository.ts](../frontend/src/demo/mockAuditRepository.ts) ofrece una implementación ficticia para la vista de demostración. | Los servicios operan mediante abstracciones de acceso a datos. Spring Data genera la implementación de los repositorios JPA. En la demo del frontend **solo existe el repositorio ficticio**; no hay todavía un adaptador HTTP para esa tabla. |
| **DTO (Data Transfer Object)** | [ActualizarPerfilRequest.java](../backend/src/main/java/pe/edu/uni/backend/dto/ActualizarPerfilRequest.java), [PerfilMedicoResponse.java](../backend/src/main/java/pe/edu/uni/backend/dto/PerfilMedicoResponse.java) y [AuditoriaEventoResponse.java](../backend/src/main/java/pe/edu/uni/backend/dto/AuditoriaEventoResponse.java) definen la entrada/salida y convierten entidades mediante `desde(...)`. | La API no necesita devolver directamente toda la entidad JPA. `PerfilMedicoResponse` selecciona campos públicos y omite el usuario de seguridad. `desde(...)` es una función de conversión; **no** es por sí sola el GoF Factory Method. |
| **Inyección de dependencias** | Constructores de [MedicoController.java](../backend/src/main/java/pe/edu/uni/backend/controller/MedicoController.java), [MedicoService.java](../backend/src/main/java/pe/edu/uni/backend/service/MedicoService.java) y [AuditoriaAspect.java](../backend/src/main/java/pe/edu/uni/backend/aspect/AuditoriaAspect.java). | Spring suministra servicio, repositorios y codificador de contraseñas. Las clases declaran qué necesitan en vez de construir esas dependencias. Hay otras clases con `@Autowired` en campos; no afirmar que todo el proyecto usa inyección por constructor. |
| **Selección de estrategia de acceso a datos / puerto y adaptadores** | [service.ts](../frontend/src/data/service.ts) publica un único `service: typeof api` y elige entre [api.ts](../frontend/src/data/api.ts) (HTTP) y [mockApi.ts](../frontend/src/data/mockApi.ts) (datos ficticios). [AuthPage.tsx](../frontend/src/pages/AuthPage.tsx) consume `service` sin elegir fuente. | En desarrollo se usa el adaptador ficticio, salvo `VITE_DATA_SOURCE=api`; producción usa el cliente HTTP. Es una variante sencilla de Strategy seleccionada al cargar el módulo, **no** un cambio de estrategia desde la interfaz. El `mockApi` no envía datos al backend. |
| **Estado compartido con Context Provider** | [SessionContext.tsx](../frontend/src/session/SessionContext.tsx) concentra sesión, `login`, `logout` y restauración; [main.tsx](../frontend/src/main.tsx) usa `SessionProvider` y protege rutas por rol. | React Context distribuye el estado de sesión a páginas y navegación. Es una solución de estado compartido de React; no presentarla como una implementación propia del GoF Observer. |
| **Manejo centralizado de errores HTTP** | [ManejadorGlobalExcepciones.java](../backend/src/main/java/pe/edu/uni/backend/exception/ManejadorGlobalExcepciones.java) usa `@RestControllerAdvice` y `@ExceptionHandler` para convertir errores en respuesta `{ "mensaje": "..." }`. | Los controladores delegan los errores a un punto común. Es una técnica transversal de Spring MVC, no un patrón GoF implementado a mano. |

## Recorrido breve para demostrarlo

1. En `PUT /medicos/me/perfil`, mostrar el método de [MedicoController.java](../backend/src/main/java/pe/edu/uni/backend/controller/MedicoController.java), la regla de [MedicoService.java](../backend/src/main/java/pe/edu/uni/backend/service/MedicoService.java), el acceso de `MedicoRepository` y la conversión `PerfilMedicoResponse.desde(...)`.
2. Señalar que [AuditoriaAspect.java](../backend/src/main/java/pe/edu/uni/backend/aspect/AuditoriaAspect.java) intercepta ese método y [AuditoriaService.java](../backend/src/main/java/pe/edu/uni/backend/service/AuditoriaService.java) persiste el evento. La consulta administrativa está en [AdminController.java](../backend/src/main/java/pe/edu/uni/backend/controller/AdminController.java).
3. En frontend, abrir [service.ts](../frontend/src/data/service.ts) y [AuthPage.tsx](../frontend/src/pages/AuthPage.tsx) para mostrar cómo el mismo formulario usa un servicio de prueba o HTTP según el entorno.

## Límites del estado actual

- El [registro de paciente](contratos/registro-paciente-v1.md) ya tiene controlador, servicio y repositorio en backend; el formulario frontend sigue usando datos ficticios por defecto en desarrollo y HTTP al seleccionar la API. El alta no crea historia clínica ni permisos médicos.
- No se han identificado implementaciones propias de Singleton, Factory Method, Observer ni Command. No conviene incluirlos como logros del equipo solo porque Spring o React los empleen internamente.
- La tabla ficticia de auditoría del Sprint 1 no prueba por sí misma la persistencia real. El backend sí contiene aspecto, repositorio y consulta de auditoría; hay que demostrar cada parte por separado.
